# Homebrew distribution

layad is distributed through [rcwsr/homebrew-tap](https://github.com/rcwsr/homebrew-tap),
not homebrew-core.

```sh
brew tap rcwsr/tap
brew install layad
```

The formula is **macOS on Apple silicon only** (`depends_on arch: :arm64`) and installs the
MLX backend. On Linux, install from PyPI or git with `uv tool install` — the dependency
markers pick the torch backend there, and `layad install-agent` writes a systemd user unit
instead of a LaunchAgent.

## Why not homebrew-core

homebrew-core builds Python formulae from sdists. The dependency closure here is 34
packages, and the blocking ones cannot be built that way:

| Package | Problem |
|---|---|
| `mlx` | 48 files on PyPI, **zero sdists** — wheel-only, ABI-tagged `cp3XX` |
| `mlx-metal` | wheel-only, 64 MiB, pulled in transitively on Darwin |
| `tokenizers`, `pydantic-core`, `hf-xet` | Rust toolchain to build from source |

There is no mlx sdist, so a core-compliant formula literally cannot be written. Core also
requires notability and bottles across platforms, and this is arm64-macOS-only by
construction. A personal tap has none of those constraints and can install wheels.

## How the formula works

`layad.rb` creates a virtualenv under `libexec` against `python@3.13` and installs
`requirements.lock` with `pip --require-hashes`, then the package itself with `--no-deps`.

The lock is generated by [`../scripts/lock.sh`](../scripts/lock.sh):

```sh
uv pip compile pyproject.toml --python-version 3.13 --generate-hashes ...
```

Two details that matter:

- **Python 3.13 is pinned in both places.** mlx wheels are ABI-tagged, so the lock and
  `depends_on "python@3.13"` have to move together. Bumping one without the other produces
  a resolution failure at install time, not a silent fallback.
- **One lock covers every supported macOS.** `--generate-hashes` emits hashes for *all*
  distributions of each resolved version, so the `macosx_14_0`, `macosx_15_0` and
  `macosx_26_0` mlx wheels are all pinned and pip picks the right one per machine.

Because a brewed Python can be revision-bumped underneath the venv, bump the formula's
`revision` when `python@3.13` moves, or reinstall.

## Releasing

```sh
git tag v0.1.0 && git push --tags
scripts/bump-formula.sh 0.1.0 ~/work/homebrew-tap   # fills in url + sha256, copies the formula
cd ~/work/homebrew-tap && git commit -am 'layad 0.1.0' && git push
brew update && brew install rcwsr/tap/layad
```

Formulae live at the tap root, next to `treesync.rb`.

The layad repo is public, so `brew install` can fetch the release tarball anonymously.
Making it private again would break installs: Homebrew has no way to authenticate to
the tarball URL.

## Choose one launchd manager

`brew services start layad` (label `homebrew.mxcl.layad`) and `layad install-agent` (label
`com.rcwsr.layad`) both register a launchd job bound to `127.0.0.1:8918`. Running both
leaves one crash-looping under `KeepAlive`. `layad install-agent` detects a brew-managed
service and refuses; the reverse is not detectable from inside brew, so check
`layad config` before starting the service.
